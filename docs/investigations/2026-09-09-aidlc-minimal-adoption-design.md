# AI-DLC 可借鉴部分：最简技术设计

状态：提案，尚未实施。日期：2026-09-09。

本次只交付设计。用户明确要求遵循 Kaola-Workflow 的最简原则。本文件不是运行记录、
backlog 镜像或已接受 ADR，不创建 claim、Mission List，也不改变已安装运行环境。

## 1. 设计结论

保留现有执行闭环。只在 Workflow Next 的 intake 和执行指引中补充两处语义，
并用一份短指南解释需求表达、验证选择和纠正的去向。

1. 对尚不清楚的任务，补足可观察结果与验收依据；已经明确的任务直接继续。
2. 文档详细程度由沟通需要决定，验证范围由行为影响与既有契约决定，两者独立。
3. 纠正按既有规则进入 issue、回归测试、项目说明或 ADR；不建设学习系统。

新增运行命令、Agent 角色、配置项、状态字段、审批点、后台任务均为零。
不建立评分器、需求解析器、阶段引擎或规则自动提取器。Mission List 保持四字段、三次写入。

## 2. 当前证据与真正的增量

以下为当前本地源码可核对的事实，而非对使用成效的推测。

| 已有机制 | 证据 | 本提案的处理 |
|---|---|---|
| 明确任务优先；读取 issue 正文与更正评论 | `templates/routing/next.skeleton.md` 的 Intake | 复用入口；补足需求不足时的判断指引 |
| 验收含义由测试作者持有，改动使受影响 PASS 失效 | 同文件 Run it | 复用；补充文档长度不能决定验证范围 |
| 收尾逐项说明 issue 哪一部分由什么证据满足 | `templates/routing/finalize.skeleton.md` 的 validation card | 原样复用，不再增加验收映射表或匹配器 |
| issue 前提被纠正时，将更正写回原 issue | 同文件 file or correct run-discovered work | 复用，不新建纠正日志 |
| Agent 维护已验证项目事实；改写 owner 内容有授权边界 | `templates/routing/init.skeleton.md`、ADR 0023 | 复用，不新增学习命令 |
| 自主执行、恢复记录与生命周期分离 | ADR 0017、`docs/architecture.md` | 保持设计边界 |

本轮没有测得“需求返工率”或“纠正重复发生率”，不能宣称存在已量化缺陷或预计收益。
提案是用户要求的设计改进；首批实际运行用于检验两处指引是否有增益。

## 3. 需求表达：在现有 intake 内补足信息

### 输入与判断

主 Agent 先读用户当前请求、已授权范围、issue 正文及更正评论、有关代码与项目约束。
判断能否确定目标行为和足以证明结果的依据。不要求固定标题、字段、字数或需求编号。

- 信息已经足够：继续现有 claim / resume 路径，不重复询问，不为了格式改写 issue。
- 缺的是可查事实：读代码、复现或查文档；查得的事实不能冒充用户价值选择。
- 缺的是已授权范围内的实现细节：Agent 决定，只在对理解有用时说明假设。
- 缺的是影响范围、兼容性承诺或验收含义的用户决策：提出最小的必要问题；同时继续独立调查。
- 用户明确只要求研究或设计：交付该结果，不由此推导出实施、建 issue 或认领的授权。

### 输出与存放

任务需求的长期权威仍是 forge issue。获授权创建或维护 issue 时，用自然语言表达
“在什么情境下产生什么结果，以及怎样确认”；会影响范围的排除项才写。
已有明确正文则引用；更正使用现有评论规则。需要展开设计时，issue 链接设计文档，
不另建一个必须同步的需求台账。没有 forge 写入授权时，先交付可审阅文字。

运行中的 Mission List 只记录可恢复成果与产物位置，不粘贴整份需求，不增加 acceptance 字段。
最终验收继续使用现有 finalize 的逐项判断。

### 分解原则与例子

优先按能独立验收的用户结果拆分；真实的共享依赖可单独处理。这里是判断原则，不是每个
issue 都必须跨越所有技术层的硬规则。

例如，“支持任务导出”需要根据现有权限和已确定格式说明：导出哪些任务、哪些字段、
空结果如何表现、如何证明用户只能导出自己有权读取的数据。格式未确定且会改变产品承诺时
才问用户。不要自行扩大到批量调度、邮件投递或后台导出服务。

最小可验收成果可以是“一次导出当前筛选结果”，实现所需各层由同一成果覆盖。
如果真正的共享接口变更必须先完成，再按依赖拆分；不为遵循纵向拆分口号制造耦合。

## 4. 验证选择：文档复杂度与风险分别判断

主 Agent 在执行前依据改变的行为、调用方、信任边界、已有测试和明确项目要求，
确定足够的验证；复杂时向测试作者交付该范围与依据。文档长短不参与降低验收要求。

| 示例 | 说明应写多细 | 验证应覆盖什么 |
|---|---|---|
| 修改说明中的失效链接 | 足以解释链接变化 | 目标与引用有效，无需业务测试 |
| 几行权限修复 | 可以很短 | 原失败输入、越权拒绝、合法访问及受影响回归 |
| 安装器路径处理变更 | 解释支持的平台与路径边界 | 受影响安装行为、空格路径、已有用户文件保护、相关运行环境 |
| 纯设计研究 | 足以审阅方案与权衡 | 来源、内部一致性、现有契约兼容；不宣称行为测试通过 |

既有强制测试、发布链、独立验收含义、UAT 边界继续有效。不能通过给任务标注“小”“快速”
或减少文档来绕过它们。没有行为改变的低影响任务，不写只复述实现的测试。

证据仍进入现有 mission result、验证 receipt 和 finalization summary；不建立
test-strategy 配置、风险档位、测试数量指标或额外测试计划文件。已有证据可用时引用它。
若候选改变，则重新判断受影响证据并重跑；已经完成的 Mission 结果不被追改。
环境不可用时写明未执行部分，不能把本地替代测试当作物理或服务验收。

## 5. 纠正：使用现有记录与维护入口

“当前纠正应执行”与“长期规则获准改写”分开判断。前者依用户当前指令推进；后者遵守
目标文件已有权限与维护规则，不把一次处理自动升级成普遍约束。

| 实际发生的纠正 | 最小去向 |
|---|---|
| 原 issue 的前提错误 | 原 issue 更正评论，执行现有收尾规则 |
| 已证明的产品缺陷 | 原修复及能区分修复前后的回归测试，遵守测试作者权限 |
| 已验证且以后仍有用的项目事实 | 已有项目文档；确实影响 Agent 行为时才维护项目说明 |
| 改变架构选择或长期约束 | 有必要时写 ADR，保留原因与适用范围 |
| 未证实的怀疑、一次性权衡 | 留在已有结果或调查文档；不提升为规范 |

写入前读目标、查重、检查与上位约束及当前事实是否冲突。已有内容足够则不写。
改写 owner-authored 项目说明仍按原规则取得授权；已授予的有效授权不重复索取。
本提案不授权修改个人记忆，也不让 finalize 每次例行询问“有什么要记住”。
若需要新会话加载修改后的项目说明，使用已有运行环境的重载规则。

这一部分首版只提供指南中的例子，不向 init 或 finalize 增加必经步骤。

## 6. 拟议源码改动

以下是未来实施的具体边界；本次未应用。

| 源文件 | 拟议改动 | 边界 |
|---|---|---|
| `templates/routing/next.skeleton.md` | Intake 内补一段“明确则继续、事实自行查、必要价值决策才询问”；Run it 内补一句文档与验证独立判断 | 不修改选择、claim、resume 顺序或 schema |
| `docs/` 下的一份短指南，建议名 `task-quality.md` | 收纳本设计第 3–5 节的精简例子 | 使用说明，不是本地 backlog，不默认全量注入上下文 |
| `docs/README.md` | 链接指南 | 使用既有文档索引 |
| `README.md`、`docs/api.md`、`CHANGELOG.md` | 实施时说明 intake 指引变化、没有新增 API，以及 Unreleased 行为变化 | 本次设计稿不把提案写成已发布功能 |

渲染文件从 routing 源统一生成，不手改任何 edition。共享全局契约、角色行为库、
claim / run-chains / sink 脚本、init / finalize 的现有机制不需要修改。
本提案不改变架构，因此无需新建“已接受 ADR”；若实施中需要状态或新的执行责任，
先重新审视设计，不能以小改动名义引入。

两处语义建议为：

> Intake：已有信息足以确定所需结果与验收依据时继续；缺失事实自行查证。只有尚未解决、
> 且会改变授权范围或验收含义的用户决策才询问。用现有 issue 表达必要结果和依据，
> 遵守 forge 写入授权；不因缺少固定格式而重写或暂停任务。

> Run it：按沟通需要决定说明详略，按行为影响和现有要求决定验证范围；短说明或小改动
> 不降低验收要求，已有充分证据可直接引用。

实施时融入现有英文上下文并去重；以上不是逐字匹配的测试契约。

## 7. 验证与实施顺序

1. 先实现两处源指引与短指南，更新相关公开说明，再用既有生成器更新产物。
2. 使用既有 routing 生成检查及其测试验证多 edition 分发；运行当前 producer 为改动选择的
   必需链和 `node scripts/simulate-workflow-walkthrough.js`。若实际改到其他表面，按影响扩展。
3. 用下列输入做新会话行为核对，保存请求、产物、必要询问及偏差。自动生成测试只能证明
   分发完整，不能证明 Agent 已理解；行为核对未执行就明确记为未执行。

| 场景 | 应观察到的行为 |
|---|---|
| 正文充分且用户授权执行的 issue | 直接推进，不生成第二份需求或例行确认 |
| 模糊需求，但缺失信息可从代码得知 | 先查事实，不把可查问题交给用户 |
| 关键验收选择未授权 | 只问必要决策，保留独立调查的进展 |
| 一行权限修复 | 说明简短，但仍覆盖越权与合法路径 |
| 用户本次纠正，但未授权改写 owner 规则 | 当前行为纠正生效；不静默改写长期规则 |
| 新证据改变当前候选 | 受影响 PASS 重验；不改写历史完成结果 |
| 纯设计请求 | 交付设计，不启动产品实施或自动 claim |

这是一份验收场景清单，不是新增固定测试平台或运行门禁。不规定文本句式、文档长度、
问题数量或测试数量来代替语义正确性。

上线观察直接复用真实任务结果：是否出现可避免的需求返工、遗漏的验收项、不必要的提问。
无可比基线时只陈述观察，不报告改善百分比。若指引增加打断或重复文档，缩减或撤回相应
措辞；无需数据迁移，已有 issue 和历史证据继续有效。

## 8. 借鉴来源与取舍

- [AWS Labs Product Agent](https://awslabs.github.io/aidlc-workflows/guide/agents/product-agent/)：
  借鉴结果、范围、验收相连的需求表达。由现有主 Agent 承接，不新增产品角色或阶段。
- [Scopes, Depth, and Test Strategy](https://awslabs.github.io/aidlc-workflows/guide/05-scopes-and-depth/)：
  借鉴说明详略与测试策略分开考虑；不引入分档、按速度降低覆盖或测试数量目标。
- [Rules and the Learning Loop](https://awslabs.github.io/aidlc-workflows/guide/09-rules-and-the-learning-loop/)：
  借鉴经验须有适用范围、未决问题不应成为规则；复用现有记录与授权，不复制日记和审批仪式。
