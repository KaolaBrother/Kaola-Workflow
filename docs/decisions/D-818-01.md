# D-818-01. `local-fallback-tool-unavailable` is retained, not retired

Date: 2026-07-26
Status: Accepted
Issue: #818 (duplicate of #817)
Relates: #817 (implemented), #598 (the incident this decision protects), #806 (superseded by #817)

## Context

Issue #818 was filed after #817 and asks for the same subtraction: delete the producer
dispatch mandate, make execution mode the orchestrator's per-unit judgment, and keep only
gate independence hard. It carries substantially better evidence than #817 did — full
session forensics of a 12.1-hour run in another repository: 33 subagent threads, 9.0 hours
of subagent time of which 95% was model reasoning and 26 minutes was command execution,
with 10–12 of the 33 dispatches assessed as avoidable or batchable.

Its design points are already shipped by #817 and its repair:

| #818 asks | shipped |
|---|---|
| D1 — producers run dispatched **or** inline at judgment, no justifier | the six plan-run surfaces carry the economics clause |
| D1 — `addCloseCompliance` records the mode instead of assuming it | the finalize-only ternary is gone; `--main-session-direct` applies to any node |
| D2 — one economics sentence for the expansion author | the composed-unit / paid-dispatch-boundary sentence, on all six adapt surfaces |
| gate independence stays hard | the fence names all three reviewing gate roles |

On one point the shipped result is **stronger** than #818 specifies. #818 asks that gate
independence be preserved "verbatim, unchanged bytes". The verbatim text named only
`adversarial-verifier` and `code-reviewer`; adversarial verification of #817 found that
`security-reviewer` had silently lost its inline prohibition when a closed enumeration of
forward roles was replaced by an open judgment grant. Implementing #818 as written would
have preserved that hole. The fence now names all three.

## The one genuine disparity

#818 D1 additionally asks that the `local-fallback-tool-unavailable` degradation framing be
"subsumed and retired", on the reasoning that inline is a first-class mode and not a
fallback.

**Decision: the token is retained, with its meaning narrowed to the literal case.**

## Rationale

The premise is accepted — inline *is* first-class. That is what "everywhere else execution
mode is your judgment, per unit" establishes, and the token no longer gatekeeps it. But the
conclusion does not follow, because the two statuses record different facts:

- `main-session-direct` — the orchestrator judged that inline was the right mode.
- `local-fallback-tool-unavailable` — the orchestrator **could not dispatch at all**: the
  agent tool was genuinely absent, or the runtime mode-refused the spawn.

Collapsing them makes a broken runtime indistinguishable from a deliberate choice. That is
not a hypothetical loss. It is the shape of the #598 incident, where a runtime configured to
refuse spawns completed an entire run with zero dispatches and self-issued gate passes. The
run-start notice that fires on genuine unavailability — naming every gate role the plan
would otherwise have dispatched — is the signal that surfaces that condition, and
`local-fallback-tool-unavailable` is what records it afterwards.

Retiring the token would therefore weaken the very notice #818 wants kept hard: the
surviving "degradation" prose is the **gate-role** notice, scoped to genuine unavailability,
not producer degradation framing. Producer degradation framing is already gone.

Subtraction is the default (see #808), but it applies to regulation that guards nothing
reachable. This token guards a reachable and previously-observed failure, and it costs no
justifier, no gate, and no approval on the execution-mode choice.

## Consequences

- #818 is closed as already implemented by #817, with this one point explicitly declined.
- `local-fallback-tool-unavailable` keeps only its literal meaning. A judged inline run
  records `main-session-direct`; the inline announcement carries no reason-token slot.
- The distinction is machine-held: the qualifying condition, including the mode-refused
  spawn case, is pinned in the contract validators and mutation-proven, so it cannot be
  removed silently the way it was once before.
- If a future run shows operators conflating the two statuses in practice, revisit — the
  argument here rests on the distinction being real and used, not on the token's existence.
