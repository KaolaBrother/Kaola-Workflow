# D-802-01. A removable blocker is a repair obligation, not a serializer: seam-checkpoint the attributed serial dirt at `open-ready`

Date: 2026-07-26
Status: Accepted
Issue: #802
Related: #615 / `D-615-01` (gated lane-group formation on parent cleanliness — **superseded in part**:
         its explicit non-goal "no out-of-band commit to clear the dirt" is reversed here);
         #616 (the `serialDegradeReason: 'parent_dirty'` telemetry label this retires at the normal
         co-open site); #641 / `D-641-01` (the consent-tier legless `observes: scratch` co-open this
         **retires**, superseded by checkpoint + full lane group); #804 (the sibling principle applied
         to the `--parallel-safe` prover: uncertainty must not impersonate evidence);
         #813 (forward relation — restoring test-path attribution shrinks the barrier-exempt band this
         decision cannot carry across the seam; see *Residual* below)

## Context

In a mixed-shape plan (serial write nodes, then a parallel write frontier) the serial siblings never
commit — under the finalize-owned-commit contract their production writes sit uncommitted in the
parent worktree. When the parallel frontier arrived, `runOpenReady` consulted the parent-clean fence
and, on dirt, **degraded the frontier to serial** (`serialDegradeReason: 'parent_dirty'`), excluded
speculative writes, or held the drain.

That degrade was the right fail-closed patch on the day it shipped. Co-opening legs over the dirt is
genuinely unsound (a leg branches off HEAD and misses the uncommitted serial context), and the
group's last-member close is caught in a two-horned deadlock:

- **Horn A** — the parent-clean fence refuses `parent_dirty` on the uncommitted serial files.
- **Horn B** — committing the dirt *after* the group baseline lands it in the merge commit, outside
  the group's declared union → `write_set_overflow` at the commit-based group barrier.

But the blocker is **self-inflicted**: the dirt is the guaranteed product of the workflow's own commit
policy, not a property of the task. Measured against the shipped doctrine — *serial is the fallback
only when a serializer is positively named, present-tense, and checkable* — `parent_dirty` is none of
the three named serializers (S1 data dependency, S2 shared irreversible effect, S3 failed environment
probe). The engine was silently serializing every mixed-shape write frontier over a state the
orchestrator itself created and could remove.

## Decision

**A serializer must be one the orchestrator cannot remove. A removable, self-inflicted blocker is a
repair obligation discharged before dispatch, and the repair belongs to the scheduler, not the plan.**

Fail-closed-to-serial is only virtuous while no sound repair exists. A sound repair exists here, it is
cheaper than the serial wall-clock it replaces, and it is mechanically checkable end-to-end.

### The seam checkpoint

When a write frontier could form a lane group but the parent carries production dirt, `open-ready`
repairs the parent instead of degrading, in five fail-closed steps:

1. **Classify** — re-run the existing `--parent-clean-check --json` fence and take its `dirty` array
   verbatim. The fence already classifies against `barrierExemptPath` with `--untracked-files=all`,
   normalizes renames to the new path, and unquotes git-quoted paths — so there is no second
   classifier and no producer/consumer drift.
2. **Attribute** — every dirty path must fall inside the union of the declared write sets of the
   ledger's **closed** (`complete`) **write-capable** rows. This is provable, not heuristic: each of
   those nodes passed its own per-node barrier at close, so its writes are already proven in-lane.
   Write-capability is *checked*, not assumed: a `complete` row with a non-empty declared set is not
   enough — the row's role must be one the grammar lets declare a write set at all, so a read-only
   role's stray declaration vouches for nothing (an unknown or absent role is not write-capable).
   The freeze validator already refuses such a plan, but attribution is the gate on a primitive that
   *commits*, so it enforces its own contract rather than inheriting it from an upstream check.
   Membership is exact-path, mirroring the barrier's own `declared.has(p)` rule. Under a schema-2
   **child epoch** the union extends across the sealed ancestor epochs, resolved through the
   validator's one verified lineage walker; an applicable-but-unresolvable lineage halts rather than
   misattributes.
3. **Commit** — `git add -- <exact dirty paths>` (stages deletions too) then a path-scoped
   `git commit -m 'kaola-checkpoint(<project>): serial→parallel seam — nodes <closed-node-ids>' -- <same paths>`,
   so a pre-staged unrelated index entry can never ride along. The commit itself is the durable
   journal — no new state file, no ledger mutation.
4. **Re-verify** — re-run the fence; only a `pass` proceeds.
5. **Proceed** — group formation continues exactly as on a clean parent. The group baseline (parent
   HEAD at open) now *includes* the checkpoint, so the serial work sits **before** the baseline and
   outside the group diff (**Horn B dissolves** — the overflow came from committing dirt *after* the
   baseline; committing *before* it is the side the barrier's own geometry implies), and legs branch
   off the checkpoint so they **see** the serial context (**Horn A and the input-freshness
   unsoundness dissolve**).

### Two outcomes, no retry loop

Either the dirt is fully attributable → checkpoint → co-open, or the run stops loudly:

- `seam_checkpoint_unattributable` — some path is vouched for by no closed node's barrier. Foreign
  bytes in the parent (a user edit, an escaped write) are an **integrity signal**; today's behavior
  buries it under silent serialization, which is worse than stopping. The halt carries the
  unattributed paths.
- `seam_checkpoint_failed` — the repair could not positively prove success: the fence could not
  enumerate the dirt (`root_mismatch`, `cannot_prove_clean`, a crashed probe), a git add/commit
  failure (the index is reset for the staged paths before halting), a post-commit fence that is not
  `pass`, or an unresolvable epoch lineage.

There is no middle "keep trying" state, and — critically — **no silent serial substitute**: "cannot
prove clean" must never become "assume clean".

### Where the halts leave the tree (one of them is not zero-mutation)

"No proceed" is not the same as "no mutation", and the contract states which is which:

- Steps 1, 1b and 2 halt **before any git write** — nothing staged, nothing committed, HEAD unmoved.
  `seam_checkpoint_unattributable` is always this shape.
- The step-3 git add/commit failure is **not a halt at all — it is a labeled DEGRADE.** The environment
  refused the commit (a content-inspecting hook veto, an unusable signing key, any git error); the
  commit did not land (git never advances the ref on a failed commit) and the index is reset for the
  paths it staged, so the tree is exactly as it was, and the caller falls back onto the pre-#802 serial
  path under `serialDegradeReason: 'seam_checkpoint_declined'`. See *Environment refusal degrades;
  integrity signals halt* below.
- The **step-4 post-commit re-fence halt is NOT zero-mutation. HEAD has advanced.** The commit is
  already in history when the re-check refuses. The refusal therefore **discloses** it: `commit` (the
  new HEAD) and `committed` (the paths that went in) ride on the halt envelope, and the operator hint
  says HEAD moved, names the commit, and says what to do next.

**Nothing is rolled back there, deliberately.** Every committed path was attributed in step 2 to a
closed write-capable node that already passed its own barrier, so the commit itself is sound; and the
likeliest cause of a non-`pass` re-fence is a **concurrent writer** landing new bytes between the two
fence spawns (the other reachable causes being a second `cannot_prove_clean` or a crashed probe). An
automatic `git reset` would destroy that writer's work — trading a loud halt for silent data loss, the
worse of the two failures. Disclosure keeps the halt loud *and* the bytes safe, and the resulting state
is exactly the crash-safe one the next section describes: a landed checkpoint over a clean-or-dirty
parent that the next `open-ready` re-fences and never re-commits.

### Call-site wiring

- **Normal co-open site** (empty running set, ≥2 disjoint writes, legs capable): dirt → attempt the
  checkpoint → on success form the group; on failure surface the typed halt. The
  `serialDegradeReason: 'parent_dirty'` label retires here — its cause class no longer exists.
- **Write-awaits-drain site** (live reads, write-only frontier): the checkpoint is attempted only when
  every live **member** is a freeze-declared `observes: scratch` `adversarial-verifier` **read** — the
  exact precondition the legless path already established, reused as-is. The quantifier ranges over the
  whole running set, not over its read subset: any member that is not a read (a live writer whose
  in-flight bytes the checkpoint must never sweep into an attributed commit, a main-session gate, an
  unrecognized kind) fails the precondition closed. Such a gate renders verdicts from
  `.cache` evidence and scratch, never the tree or refs, and `git commit` is tree-content-neutral (it
  touches index + refs, never working-tree bytes), so no live observer's inputs change. With the
  parent clean, the ordinary leg-contained group co-open follows, and **the legless single-writer
  exception retires** — strictly stronger: N writers instead of 1, leg containment instead of a
  contract-only observation promise. Non-scratch live readers or a live gate hold as before.
- **Speculative-write site** (a gate is live by definition): the `parent_dirty` exclusion **stays** —
  a live gate's verdict window may span refs and diffs, so checkpointing under it is not obviously
  sound. In practice the seam is already clean when speculation begins.

### Operator escape hatch

`KAOLA_SEAM_CHECKPOINT=0` (resolved in the forge-neutral adaptive-schema module alongside the existing
toggles, default ON) restores the **`parent_dirty` serial degrade** — the single serial write at the
normal co-open site, and the `write_awaits_drain` hold at the drain site — mirroring the
`KAOLA_PARALLEL_WRITES=0` recovery posture.

**Scope, stated exactly.** The opt-out restores the serial degrade *only*. It does **not** resurrect
the legless single-writer co-open that used to fire over a dirty parent behind a scratch-observation
gate: that path is retired **unconditionally**, as a separate and deliberate tightening, and no toggle
brings it back. A seam that once legless-co-opened therefore **holds** under the opt-out. Both changes
point the same way — the toggle is never *less* strict than the repair it replaces — so this is a
fail-closed escape hatch, not a time machine. (The retirement is not behind the toggle on purpose:
resurrecting a legless writer over a dirty parent would reinstate an unsound co-open, and a recovery
switch must never be the thing that reopens one.)

## Soundness notes

- **Serial per-node barriers are unperturbed.** Their base is a full-worktree snapshot at open, and at
  the normal co-open site the running set is empty — no open serial node exists whose base could
  straddle the checkpoint.
- **Mid-run commits are precedented, not novel.** Every lane-group last-member close already creates a
  merge commit on the feature branch, so "finalize owns the commits" already really means "node
  *agents* never commit". An orchestrator-owned checkpoint respects that reading. Finalize already
  sweeps whatever remains on a branch carrying mid-run commits; discard already handles one.
- **Crash safety is idempotent by construction.** A crash after the commit but before the group opens
  leaves a clean parent — the next `open-ready` re-runs the fence, finds `pass`, and forms the group;
  nothing re-commits. `reconcile-running-set` is untouched.

## Rejected alternatives

- **Relaxing `--parent-clean-check` or the group barrier** to treat closed nodes' declared sets as an
  allowband *without* a commit — reopens the floated-slip laundering hole the fence exists to close.
  Rejected once before; stays rejected. This decision does not relax any fence: it *satisfies* them.
- **Re-anchoring the group baseline** past the dirt — a misdiagnosis. This design instead moves the
  commit *before* the baseline, which the original Horn-B analysis itself identifies as the
  geometrically correct side.
- **A retry-loop repair** — two outcomes only; loops trade correctness pressure for liveness theater.
- **A new standalone script file** — the checkpoint lives inside the adaptive-node aggregator, so the
  common-script set, the install manifest, and every runtime inherit it through existing distribution
  with zero new registration surface.
- **Silently serializing over unattributable dirt** (the prior behavior) — buries an integrity signal.
  The halt is the point.

## Deferred (named so they are not silently dropped)

- **Checkpoint under a live gate** — requires proving no gate brief can observe HEAD or refs.
- **Per-close commits everywhere** (every serial close commits its own declared set, unifying with how
  legs already work) — eliminates the dirt class at the root, but touches every snapshot-based
  barrier, finalize, resume, and all editions.
- **`lane_group_live` under the same principle** — that hold exists only because `running-set.json`
  carries exactly one lane-group descriptor at a time: an implementation limit, not a task serializer.

## Consequences

- A mixed-shape plan now runs its parallel write frontier **in parallel**, where before every such
  frontier serialized invisibly.
- Two new typed halts exist at `open-ready`. Both are loud and both carry operator hints. Neither ever
  flips a ledger row, writes a running set, or leaves a partial index. **One of them can leave a
  landed commit**: the step-4 post-commit re-fence halt, which discloses the advanced HEAD on the
  refusal envelope (see *Where the halts leave the tree* above). Every other halt shape leaves HEAD
  unmoved.
- The scheduler's degrade vocabulary is now honest: `serialDegradeReason` names a *real* serializer or
  the operator's own opt-out, never a condition the scheduler could have removed.
- A consumer repo's git configuration can no longer halt a run at a scheduling seam — and the seam does
  not bypass their content inspection to achieve it. See the section below.

### Environment refusal degrades; integrity signals halt

The checkpoint fires *mid-schedule*, unlike every finalize-time commit, so a repo-local hook, a
key-less `commit.gpgsign true`, or a repo with no configured `user.email`/`user.name` could turn a
routine seam repair into a hard halt — states that merely serial-degraded before the repair existed.

The first attempt at this fix added `--no-verify`, reasoning that the checkpoint is internal scheduler
bookkeeping. **That reasoning does not hold.** The seam checkpoint is the ONLY scheduler commit that
lands *user production source*: `kw-stub` is an empty `.cache` evidence-stub commit, and
`kw-leg`/`kw-synth` are in-lane and merge commits. Bypassing `pre-commit` therefore disarmed the
consumer's **content inspection** — a secret scanner, a license or policy gate — on exactly the bytes
it exists to see, and permanently: nothing re-examines them once they are in history, and
`kaola-workflow-claim.js` (which would have caught them at finalize) runs no such bypass. The check
was *defeated*, not deferred.

The corrected design splits consumer git configuration by **what it actually asserts**:

- **Attribution — identity and signing — is overridden.** All four scheduler commit sites share one
  `SCHEDULER_COMMIT_CONFIG` (`-c user.email=kaola-workflow@local -c user.name=kaola-workflow
  -c commit.gpgsign=false`). A signature asserts *authorship*, and an identity *names the author*;
  neither says anything about the bytes, so neither may halt a run — and the scheduler must not sign
  as the human author regardless.
- **Content inspection — `pre-commit`, `commit-msg`, `prepare-commit-msg` — is honored, never
  bypassed.** No site carries `--no-verify`. (The old in-code audit of what `--no-verify` made inert
  was also an overclaim: it covers only `pre-commit` and `commit-msg`, so a `prepare-commit-msg` hook
  exiting 1 still halted the seam.)

When the environment refuses a scheduler commit, the seam **degrades to the pre-#802 serial path**
under the typed label `serialDegradeReason: 'seam_checkpoint_declined'`, with a `seamCheckpointDeclined`
object carrying git's own error. This is not the silent serialization this decision forbids: *silent*
is the defect, and the label states a checkable present-tense fact — the repair was attempted and
refused by this host. Wedging a run that would otherwise complete is strictly worse than completing it
serially. The `kw-stub` commit degrades the same way (abandoning group formation, dropping every
baseline the call recorded, and opening a single serial write); its former `stub_commit_failed`
refusal was a dead end no retry could clear. `kw-leg`/`kw-synth` gain the same attribution overrides —
a key-less signing config used to let a group co-open and then die at the last-member close with
`leg_capture_failed` — but have no serial path left to degrade onto once legs exist, so a
content-inspecting veto there stays the existing typed refusal.

**Only ENVIRONMENT refusal degrades.** The integrity signals stay loud halts:
`seam_checkpoint_unattributable` (foreign bytes in the parent) and the post-commit fence.

## Residual: the barrier-exempt band is not carried across the seam

The claim that the input-freshness gap "dissolves" holds for the band the checkpoint can see, and
**only** for that band. It must be read with this limit attached.

`--parent-clean-check` classifies through `barrierExemptPath`
(`isWorkflowArtifactPath || isBarrierInvisible || isTestLikePath`), so an uncommitted change under
`docs/**`, `README.md`, `CHANGELOG.md`, `kaola-workflow/**`, or any test-like path **never enters the
fence's `dirty` array**. What the checkpoint never sees, it never commits: a parent carrying only
exempt-band changes re-fences as `pass` and the checkpoint is a no-op
(`{ ok: true, committed: [], commit: null }`).

The consequence is precise: **closed serial siblings' uncommitted docs / CHANGELOG / test bytes stay
in the parent worktree, and the legs branch off a HEAD without them.** A leg member that reads those
files sees the pre-serial version. That is a genuine residual of exactly the kind the retired legless
`observes: scratch` exception used to govern — the same band, approached from the other side.

Why this is accepted rather than fixed here:

- **The exemption is not this decision's to change.** `barrierExemptPath` is the fence's own
  classification, shared with the per-node barrier and the finalize sweep; widening it at the seam
  would fork the classifier and reopen the producer/consumer drift this design exists to avoid.
- **The residual is bounded and non-silent in the direction that matters.** Exempt-band bytes are, by
  the barrier's own definition, the ones a node may write *without declaring*, so they are not
  attributable at the seam either — committing them would be the laundering move this decision
  explicitly rejects.
- **The remaining leg-visibility gap is reconciled downstream.** The mandatory post-dominating
  synthesizer merges every leg into the parent that still holds those bytes, and finalize sweeps
  whatever remains on the branch.
- **The band is expected to shrink.** #813 restores test-path attribution (it removes the
  `isTestLikePath` exemption from barrier attribution), which would move test-like paths out of the
  exempt band and therefore *into* the checkpoint's reach, with no change to this design. That is a
  forward relation only — it is deliberately not implemented here.
