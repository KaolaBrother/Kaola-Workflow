status: open
workflow_project: issue-969
next_step: Found by the #968 run-gap sweep, and hit directly during that run. Neither sync-opencode-edition.js --check nor sync-kimi-edition.js --check runs in any of the four chains; both live only under npm run test:kaola-workflow:editions, which is in neither npm test nor the full tier. Measured: after editing three routing skeletons, generate-routing-surfaces --check reported all 18 tracked surfaces byte-matching at exit 0 while every one of the six edition trees still carried the old wording, and only an explicit six-invocation sync propagated it. The same run also found the four gitlab/gitea edition trees already stale against e4522be9, because install-all.sh --forge=github regenerates the github trees only; that drift had been sitting green until the run regenerated it incidentally. The trees are gitignored, so neither git status nor a diff review surfaces the staleness either. These are consumer-facing surfaces — the prose an opencode or kimi user actually reads — and the failure is silent in both directions, since each tree stays self-consistent and its own suite passes once someone finally runs it. SPECIFY THE RESULT, NOT THE MECHANISM: the wanted outcome is that a skeleton edit cannot reach a green four-chain receipt while an edition tree still carries the old prose; whether that is adding the two --checks to the chains, folding them into generate-routing-surfaces --check, or something else is the implementer's call, as is whether the check belongs in every chain or only where the diff touches templates/routing/. Note the neighbouring asymmetry already on ADR 0017's watch list: opencode is the edition missing a remediation guard its kimi sibling has.
