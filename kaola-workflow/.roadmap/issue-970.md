title: A mission-list item can carry a result while still reading in-flight, and the run archives silently
status: open
workflow_project: issue-970
next_step: Observed with a count, not derived — the #968 run archived with 7 of 17 items carrying a result and still reading status: in-flight, while the run itself was complete (four chains green, walkthrough 209/209, issue closed, sink clean). Cause was the third write moment happening by halves: outcomes written with edits whose match string omitted the status line, then patched around twice by inventing a status_note field, which put three non-spec field names into the durable record (status_note, result so far, earlier result). That record is repaired in a follow-up commit; the class is what this issue is about. Severity comes from the resume rule, not from tidiness: mission-list.md is the artifact a successor reads first, in-flight items are documented as the only decision to make, and an item reading in-flight WHILE carrying its own result inverts "look for the work, not the worker" — a successor re-dispatches finished work, and the result line that would correct it is the line the rule does not send it to. The archive is read as evidence by later runs, so the damage outlives its run. DO NOT BUILD A GATE: the record is deliberately not attested, not frozen and not machine-verified, stated as intentional in CLAUDE.md and ADR 0017, and a refusal would be a mechanism justified by "the agent might get this wrong". What changed is only that it stopped being might. SPECIFY THE RESULT: at finalize, a run whose record shows an item with an outcome but a non-done status is TOLD so — the same measure-and-report shape finalize already uses for the chain receipt and changed paths, landing on the envelope and in finalization-summary.md, with no refusal and no new required field. Whether that lives in the finalize transaction, the gap sweep, or elsewhere is the implementer's call. One correctness note for whoever takes it: the condition is outcome-present-and-status-not-done, NOT status-is-in-flight — a genuinely in-flight item with no result at finalize is a different and louder problem, and conflating them makes the report useless exactly where it matters.
