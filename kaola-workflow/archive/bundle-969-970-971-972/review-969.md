## Findings, most severe first

### R1 (LOW) — bare-repo and submodule postures put the generated tree inside a git metadata directory, contradicting the shipped fallback rule

- **Where**: `scripts/sync-opencode-edition.js:74` (`TREE_ROOT = resolveMainRoot(REPO)`) and its
  contract comment at `:70-73`; twin at `scripts/sync-kimi-edition.js:72`. Mechanism:
  `scripts/kaola-workflow-adaptive-schema.js:513-516` (`mainRootFromCoord` returns the coord root
  verbatim when its basename is not `.git`).
- **The shipped rule** (the candidate's own comment): the tree belongs to the main checkout; "where
  there is no main checkout to resolve … the tree belongs where this script itself does, and never
  in the process cwd."
- **Reproduction (MEASURED)**:
  - Bare + worktree: `git clone --bare fx bare.git; git -C bare.git worktree add bare-wt main` →
    `--print-tree-root` from `bare-wt` prints `…/bare.git`; an install from `bare-wt` writes
    `bare.git/.opencode/` and deploys from it (14 agents, exit 0).
  - Submodule: `git submodule add fx sub` in a superproject → `--print-tree-root` from `sub` prints
    `…/super/.git/modules/sub`; an install writes `super/.git/modules/sub/.opencode/` and deploys
    from it (14 agents, exit 0).
- **Wrong behaviour**: in both postures there *is no main checkout*, yet the tree does not fall back
  to "beside the script" — it lands inside a git metadata directory (a bare repo's gitdir; another
  repository's `.git/modules/`). Both sync and installer agree on the location, so the install
  itself succeeds with full counts; nothing is overwritten or lost (the prune paths only look inside
  the generator-owned `.opencode*/`/`.kimi*/` subtrees).
- **Why it matters / why low**: a bare-hub layout (bare repo + all checkouts as worktrees) is a real
  user posture, and for that user *every* checkout is linked — the trees permanently accumulate
  inside `repo.git/`. Surprising pollution and a contract-comment falsified by its own code, but no
  wrong deploy, no data loss, and the two postures are uncommon for this repo's install story. The
  cheap shape of a fix: treat a coord root whose basename is not `.git` as "no main checkout" and
  fall back to `REPO` for tree placement (or amend the shipped comment to name the third outcome).

- **True severity: low.** With the fixed root line the guard is nearly unreachable: `--check ||

## The dispatch's six attacks — what I ran and what held

### 1. The root split — SOUND (one deviation = R1)

- **Resolution matrix (all MEASURED via `--print-tree-root`, cwd-independence checked by invoking
  from `/` and from `$HOME`)**: main checkout → itself; linked worktree → the main checkout; fresh
  clone → itself; no-git copy (consumer posture) → beside the script, **never cwd**; deleted-main
  worktree → git fails, falls open to beside the script; bare-worktree / submodule → R1. Both sync
  scripts and both installers give one answer per posture (same computation, same file).
- **Every tree-touching path moved; no canonical read did (MEASURED + swept)**: the only remaining
  `path.join(REPO, …)` sites in both sync scripts are `agents/`, `hooks/`,
  `templates/opencode/plugins/`, `opencode.json`, and the canonical `read()` helper; the only
  `.opencode`/`.kimi` segment producers are `outDirs()` (TREE_ROOT-rooted) and the `treeLabel`
  label helpers whose output is joined via `treePath()`. Behavioural proof in the fixture: a marker
  planted in the **worktree's** skeleton reached **all six of main's trees** through the one
  mandated step (6/6 files carry it), no `.opencode*`/`.kimi*` was created in the worktree, the 18
  tracked surfaces landed in the worktree only (marker in wt's `commands/workflow-next.md`, absent
  from main's) — sources read from the invoking checkout, tree written to main, exactly the split
  claimed. `--check` agrees with `--write` about the root (suite A31 pin; suites green below).
- **The observed failure is closed (MEASURED)**: the #968 shape — sync from a worktree, delete the
  worktree, main stale — cannot recur, because the worktree run writes main's trees directly.

### 2. The race and the unmerged-prose cost — genuinely bounded (MEASURED)

- The question that matters: *can a user's installed surfaces carry never-merged prose with nothing
  to correct it?* **No — unless the user installs from the branch checkout itself, which is the
  request.** Demonstrated end-to-end: with main's tree carrying the worktree's marker prose, a
  hermetic `install-opencode.sh` run **from main** exited 0, deployed 14+3, and the deployed
  `workflow-next.md` did **not** contain the marker — the installer's `--check || --write` heals the
  tree from *its own* checkout's canonical before every copy. An install **from the worktree**
  deploys the branch prose (marker present) — that is installing a branch, not a leak.
- Two-worktree race: last render stands on the shared tree, but every deploy re-heals first, so each
  install is self-consistent; the residual is a millisecond heal-to-copy TOCTOU needing two
  concurrent operations by the same user. Accepted cost, honestly documented in the code comment.
- Live in this repo now (MEASURED, read-only): real main's `sync-opencode-edition --forge=github
  --check` exits 1 on exactly one file (`kaola-workflow-finalize.md` — this branch's unmerged S2
  prose). Any main-posture install heals it; the editions suites report it loudly at D0 rather than
  rewriting it (their D0 exits before the self-provision `--write`).

### 4. The spawn — SOUND (all three failure modes MEASURED)

- Child exits non-zero (stub exiting 7): `--write` exits **1**; the child's stderr is surfaced
  (`stdio: 'inherit'`), and the generator's own line names script and status. No pipe sits between
  the child and the verdict — `spawnSync(...).status` is read directly.
- Sync script absent: skipped silently, `--write` exits 0 (a checkout without edition generators —
  the intended consumer posture).
- Child killed by signal: `status` is `null`, `null !== 0` catches it, exit 1 ("exited null" —
  slightly opaque, loud).
- There is no path where `--write` exits 0 with a failed child: the exit is
  `if (refreshPresentEditionTrees() > 0) process.exit(1)` and every non-zero/none status increments.
  The 18 tracked surfaces are written before the refresh, so a failed refresh leaves them updated
  and the exit red — partial but honest.
- Hang: `spawnSync` carries no timeout, so a wedged child wedges `--write`. Hypothesis only — the
  children are pure local computation with no prompt, no network, no stdin read; no reachable
  trigger identified. Not admitted.
